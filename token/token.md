1. Close all irrelevant sidebars and output panels
Reduce UI state information (like terminal logs and Problems panel warnings) transmitted to AI, preventing them from being mistakenly packed as context.

2. Use .vscode/settings.json to exclude large files
Configure "files.exclude" and "search.exclude" to let AI tools automatically skip directories like dist/ and node_modules/, reducing file scanning scope from the source.

3. Keep the active file "lean"
Since AI often reads the currently focused file by default, develop the habit of opening only necessary files and closing unrelated long-file tabs.

4. Break long prompts into multiple short messages
Sending a single 2,000-word question incurs a one-time high cost; splitting it into 3–4 sequential messages consumes fewer total tokens because the already-loaded system prompt can be reused.

5. Regularly clean cache files under .vscode/
Delete historical index files like .vscode/.copilot-* or .mcp-cache to prevent old data from being reloaded into the context.

6. Leverage VS Code's "selection range" feature
Highlight a specific function or code block before triggering AI commands (e.g., Copilot Inline Chat), so the input is automatically scoped to the selection rather than the entire file.

7. Use an "inside-outside" workflow
Draft long questions in an external editor (like Notepad) and refine them before pasting into VS Code, avoiding multiple context retransmissions caused by repeated in-editor edits.

8. New Chat
Starting a new chat after completing each independent subtask allows you to "peek" at the cached context from previous sessions for continuity, while actively isolating completed lengthy content to prevent it from persistently occupying the current conversation's token window.

9. Installing standalone sub-MCP plugins 
Instead of large bundled collections significantly saves tokens, because collection plugins inject lengthy schema definitions and descriptions for all sub-tools into the context at once, whereas standalone plugins load only the minimal toolset currently needed, avoiding redundant declarations from consuming the window.

10. precise instructionss
When coding or using MCP, prioritize "precise instructions" (e.g., "read lines 50-80" or "query records with status='active'") over vague requests (e.g., "look at this file" or "check the data"), because precise instructions dramatically reduce the extra token consumption generated by MCP's guesswork, option enumeration, and redundant validation responses.

# Agent & Skill Documentation Token Optimization Tips

## 1. Use table instead of prose description
Replace lengthy text explanations with structured tables to reduce token usage by 40-50% while improving readability.

```markdown
# Bad
When a user requests test scenario generation, the agent first reads the Confluence page,
then analyzes the feature document, and finally generates test scenarios...

# Good
| User Request | Phase | Skill |
|-------------|-------|-------|
| "Generate tests for page {id}" | Full pipeline | All 3 skills |
| "Analyze this feature doc" | Phase 2 only | feature-analyzer |
```

## 2. Reference instead of duplication
Use relative file paths to reference shared content rather than duplicating the same content across multiple files, saving 60-70% tokens.

```markdown
# Bad (in java-ddd-architecture/SKILL.md)
## Naming Conventions
- Use PascalCase for class names
- Use camelCase for method names
...

# Good
## Basic Standards
Follow naming conventions in [java-code-style](../java-code-style/SKILL.md)
```

## 3. Compress code examples to core patterns
Show only essential code patterns instead of complete runnable implementations, reducing code size by 50-60% while maintaining clarity.

```java
// Bad: 50+ lines with imports, getters, setters
public class Order {
    @AggregateIdentifier
    private OrderId id;
    private CustomerId customerId;
    // ... 20+ lines of implementation
}

// Good: 10 lines showing the pattern
@Aggregate
public class Order {
    @AggregateIdentifier
    private OrderId id;
    
    @CommandHandler
    public Order(CreateOrderCommand command) {
        apply(new OrderCreatedEvent(...));
    }
}
```

## 4. Use YAML/JSON for structured data
Replace verbose text descriptions with structured data formats, saving 60-70% tokens and making content machine-parseable.

```yaml
# Bad
The password field must be between 8 and 50 characters. If it's less than 8 or more than 50, the system should reject it and show an error message...

# Good
validation:
  field: "password"
  type: "length"
  min: 8
  max: 50
```

## 5. Implement three-layer architecture
Separate content into lightweight agents (1-2KB), medium skills (5-10KB), and external references (on-demand), reducing initial load by 70-80%.

```
agent.md (lightweight) → Core definition + skill references
skill.md (medium) → Implementation logic + key examples
external-docs (on-demand) → Detailed implementation + complete cases
```

## 6. Use decision tables for conditional logic
Replace complex nested if-else descriptions with decision tables, saving 40-50% tokens while improving clarity.

```markdown
# Bad
If the user is active and attempts < 5 and credentials are valid, then success.
If the user is active and attempts < 5 but credentials invalid, then error.
If the user is active and attempts >= 5, then locked.
If the user is inactive, then error...

# Good
| Active? | Attempts<5? | Valid? | Result |
|---------|-------------|--------|--------|
| Y | Y | Y | Success ✅ |
| Y | Y | N | Error |
| Y | N | - | Locked |
| N | - | - | Inactive |
```

## 7. Template repetitive content
Create reusable templates for repeated structures, reducing duplication by 70-80%.

```yaml
# Template
test_case_template:
  preconditions: "${user_state}"
  steps: "${action}"
  expected: "${result}"

# Usage
test_cases:
  - { user_state: "active", action: "valid login", result: "success" }
  - { user_state: "locked", action: "login", result: "error" }
```

## 8. Minimize comments and documentation
Remove redundant comments that explain "what" instead of "why", focusing on essential documentation only.

```java
// Bad
// Get order by ID
Order order = orderRepository.findById(orderId);

// Validate the order
order.validate();

// Save the order
orderRepository.save(order);

// Good
Order order = orderRepository.findById(orderId);
order.validate();
orderRepository.save(order);
```

## 9. Use YAML front matter for metadata
Declare key information in structured front matter instead of embedding it in prose paragraphs.

```yaml
---
name: "test-scenario-agent"
description: "Converts Confluence docs to test scenarios"
pipeline: ["confluence-reader", "feature-analyzer"]
output: ["markdown", "gherkin", "json"]
---
```

## 10. Employ abbreviations and conventions
Define standard abbreviations in a central glossary to shorten repeated terms.

```yaml
conventions:
  AC: "Acceptance Criteria"
  BR: "Business Rule"
  TC: "Test Case"
  VO: "Value Object"
  AR: "Aggregate Root"
```

## 11. Use "See reference" for detailed content
Move comprehensive examples and detailed implementations to external files, keeping main documents lightweight.

```markdown
## Aggregate Pattern
```java
@Aggregate
public class Order { /* pattern */ }
```

**Complete Implementation**: [examples/order-aggregate-full.java](../examples/order-aggregate-full.java)
```

## 12. Apply progressive disclosure pattern
Show basic patterns in main content, advanced features in optional sections.

```markdown
## Basic Usage
```java
Order order = new Order(orderId, customerId);
```

## Advanced Features
<details>
<summary>Click to expand</summary>
```java
Order order = Order.builder()
    .id(orderId)
    .customerId(customerId)
    .build();
```
</details>
```

## 13. Use links instead of inline content
Reference external documentation via markdown links rather than including full content.

```markdown
# Bad
The testing strategy follows these principles: [20 lines of explanation]

# Good
The testing strategy follows [testing-best-practices.md](../testing-best-practices.md).
```

## 14. Optimize for AI context window
Structure content so AI can find relevant sections quickly without reading entire files.

```markdown
## Quick Reference
| Task | Section | Lines |
|------|---------|-------|
| Create aggregate | Domain Model Patterns | 150-200 |
| Write tests | Testing Strategy | 300-400 |
```

## 15. Use "Example" sections sparingly
Show one good example instead of multiple variations, or use tables to compare approaches.

```markdown
# Bad
Example 1: Using builder pattern...
Example 2: Using factory pattern...
Example 3: Using constructor...

# Good
| Pattern | Use Case | Complexity |
|---------|----------|------------|
| Builder | Many optional fields | Medium |
| Factory | Complex creation logic | High |
| Constructor | Simple objects | Low |
```

## Token Saving Estimation

| Strategy | Token Reduction | Readability Impact |
|----------|----------------|-------------------|
| Table instead of prose | 40-50% | Better structure |
| Reference vs duplicate | 60-70% | Requires navigation |
| Compress code examples | 50-60% | Needs completion |
| YAML/JSON format | 60-70% | More parseable |
| Three-layer architecture | 70-80% | Better modularity |
| Decision tables | 40-50% | Clearer logic |
| Template repetitive content | 70-80% | Requires understanding |
| Minimize comments | 30-40% | Cleaner code |
